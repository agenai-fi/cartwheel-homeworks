3. How Harbor works and where Cartwheel fits

Harbor runs repeated trials of an agent on tasks, each trial in a fresh Docker container, and records a reward per trial. The repo supplies two adapters: the dataset adapter turns cases into tasks; the agent adapter runs Cartwheel inside each task.

Reward. 1 only if every check passes and every judge verdict equals its expected value (reward.toml: aggregation = "all-pass"), else 0. Assertions produce no reward.

Result layout in Harbor 0.23.0. The job's result.json holds aggregate stats only, with no trial_results list. Each trial writes its own <trial>/result.json (verifier_result.rewards.reward, exception_info, started_at). harbor_adapter/summary.py load_trial_results reads those files ordered by started_at; the supplied code expected trial_results.

Where to look when a trial fails. The verifier log dir /logs/verifier is copied to <trial>/verifier/:

  • reward.json: the reward. reward-details.json: score per component (checks, judge_<mode>), so it tells you whether the checks or the judge caused a 0.
  • judge_<mode>.json (judge cases only): judge_id, model, expected, verdict, critique, and the exact input the judge saw. The critique is also printed to test-stdout.txt.
  • For a code-check failure, reward-details.json shows only the aggregate cartwheel_code_checks criterion; read the tool calls in <trial>/agent/cartwheel-result.json. Example: all 9 failed e-010 trials in Part E called find_order and get_order and never escalate_to_human.
  • Browse jobs in a web UI with harbor view .harbor/jobs.

5. Judge validity (A0)

Problem. Two defects in the supplied adapter meant Harbor would not run the judge HW5 validated. (1) load_frozen_judge took the highest frozen version: v5 (gpt-5.5) instead of the accepted v4 (gpt-4o-mini); both files have "status": "frozen". (2) Harbor's judge input had no system prompt, no tool names and no original order of text and tool steps (tool calls grouped before the reply), and the call set no temperature. The handout requires the frozen prompt, model, input and verdict parser.

Measurement on the 57 HW5 test traces (28 labeled Pass, 29 Fail), judge v4. TNR = Pass kept, TPR = Fail caught; flips = verdicts that differ from HW5's recorded verdicts.

ArmTNRTPRflips
HW5 recorded verdicts20/28 = 0.7119/29 = 0.66-
Harbor input as supplied16/28 = 0.5722/29 = 0.7611
Harbor input, temperature 018/28 = 0.6421/29 = 0.7210
HW5 input, temperature 019/28 = 0.6820/29 = 0.694

Temperature alone removed 1 flip; restoring the input removed 6 more. The Harbor input shifted errors toward false Fails (TNR 0.71 to 0.57): statements sourced from the system prompt or a named tool look unsupported when those are missing.

Fix. Pin file eval_cases/judges.json = {"unsupported_claim": "unsupported_claim-v4"}; load_frozen_judge raises when several versions are frozen and none is pinned, or when the pin names a judge that is not frozen. One shared renderer, replay/judge_input.py (flatten_messages, judge_completion_kwargs), used by both HW5 analysis and the Harbor verifier; the runtime records ordered events and the system prompt. Temperature 0 (judge_completion_kwargs returns {} for gpt-5/o models, which accept only the default). Contract test: all 141 HW5 judge inputs render byte-identical to scale.judge_rows.

Lesson. A judge's TPR/TNR hold only for the input it was validated on. Change the input format and you have a different, unmeasured instrument.

Sources: analysis/spikes/2026-11-14-hw6-judge-input/ (run.py; results.json, results-harbor_t0.json, results-hw5_t0.json, rates recomputed from the label and verdict fields), analysis/state/judges/unsupported_claim-v4.json, -v5.json, replay/rollout.py load_frozen_judge, replay/judge_input.py, tests/test_replay_harness.py, analysis/state/hw5_trace_inputs.json (141 records).

6. Part B: pass@k and pass^k

pass@k (capability: at least one of k attempts succeeds)
1 - C(n-c, k) / C(n, k); 1 when n - c < k
e-010 baseline 10100, n = 5, c = 2:
pass@1 = 0.4; pass@3 = 1 - C(3,3)/C(5,3) = 1 - 1/10 = 0.9
pass^k (reliability: all k attempts succeed)
C(c, k) / C(n, k); 0 when c < k
e-010: pass^5 = 0 (c = 2 < 5).
A regression case at 5/5: pass^5 = 1. At n = 5, pass^5 = 1 exactly when the gate passes.

case_passes(kind, passes, n): a regression case blocks when passes < n; a capability case always returns pass.

10. What went wrong and how it was fixed

  1. Wrong judge. The loader silently took v5. Fix: pin file plus a loader that refuses ambiguity.
  2. Wrong judge input. No system prompt, tool names or original order; no temperature; 11 of 57 verdicts flipped. Fix: one shared renderer, temperature 0, byte-identical contract test over 141 inputs.
  3. Harbor 0.23.0 result layout. No trial_results list in the job result.json. Fix: load_trial_results reads per-trial files ordered by started_at.
  4. Critiques not stored. The e-002 baseline ran before the generated judge saved anything; its critiques were recovered by re-judging (the one-off script was later removed). Fix: the judge writes judge_<mode>.json (verdict, critique, input) and prints the critique to test-stdout.txt.
  5. Regression cases come from situations that work. Cases built from HW4 Fail traces baselined as capability (e-002 and e-004 at 0/5, e-010 at 0.4).
  6. Judge noise makes judge cases rarely regression. At the average Pass-kept rate 0.68, a correct reply passes 5 of 5 judge calls with probability about 0.68^5 = 0.15 if the misses were independent. Only e-011, a one-line price lookup, reached 5/5.
  7. Publishing. Single public commit on top of hw5; [skip ci] for follow-up commits; PR base hw6-base so merges never touch hw5.
  8. Demo labels restored (b725f13): the upstream unsupported_policy_claim.jsonl removed in HW4; course tests test_m2_* rely on it.
  9. offline checks red on one course test that expects the demo mode in the HW4 taxonomy; known and disclosed in the PR.

Sources: sections above; git log on hw6 (0798e20, b725f13, 0e269e6); PR #2 body.
